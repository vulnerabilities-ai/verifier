ANT-2026-YZAKBHEW: Heap-buffer-overflow in hermes.cpp:262

Hermes's TextEncoder.prototype.encodeInto passes its destination argument through getTypedArrayBuffer() in JSIUtils.cpp, which reads the buffer, byteOffset, and byteLength properties off the object without verifying the object is a real TypedArray or that the claimed length fits the backing ArrayBuffer. A 646-byte JavaScript PoC supplies a plain object wrapping an 8-byte ArrayBuffer but claiming byteLength 1000000, together with a 100000-character string. convertUTF16ToUTF8BufferWithReplacements then writes UTF-8 output far past the 8-byte heap block. ASAN confirms a heap-buffer-overflow WRITE inside the 8-byte region allocated by JSArrayBuffer::createDataBlock, reproducing identically across three fresh container runs (exit 134).

Target

Project: facebook/hermes
Location: hermes.cpp:262

Technical Details

ASAN: "heap-buffer-overflow on address 0x602000005018 ... WRITE of size 1" in convertUTF16ToUTF8BufferWithReplacements (UTF8.cpp:149:19). The root cause is getTypedArrayBuffer() duck-typing the destination: it trusts user-controlled byteLength/byteOffset properties instead of validating them against the real ArrayBuffer size, so encodeInto is handed a buffer pointer/length pair where length vastly exceeds the actual 8-byte allocation.

Crash trace:

The PoC is a 646-byte JavaScript file that exploits a heap-buffer-overflow vulnerability in Hermes's TextEncoder.encodeInto implementation. The exploit works by passing a plain object with a spoofed `buffer` (8-byte ArrayBuffer), `byteOffset` (0), and `byteLength` (1000000) to TextEncoder.prototype.encodeInto, along with a large string ("A".repeat(100000)). The underlying C++ code in `getTypedArrayBuffer()` (JSIUtils.cpp) trusts these duck-typed properties without validating them against the actual ArrayBuffer size, causing `convertUTF16ToUTF8BufferWithReplacements` to write far past the 8-byte heap allocation.

All 3 reproduction runs in a fresh Docker container produced identical results:
- Error: AddressSanitizer: heap-buffer-overflow on address 0x602000005018
- Type: WRITE of size 1
- Crashing function: hermes::convertUTF16ToUTF8BufferWithReplacements at /workspace/repo/lib/Support/UTF8.cpp:149:19
- Called from: textEncoderEncodeInto at /workspace/repo/API/hermes/extensions/TextEncoder.cpp:139:11
- Overflowed allocation: 8-byte region allocated by JSArrayBuffer::createDataBlock at /workspace/repo/lib/VM/JSArrayBuffer.cpp:252:42
- Exit code: 134 (all 3 runs)
- No OOM or timeout indicators present

Reproduction

  1. Allocate a small ArrayBuffer (e.g., 8 bytes).
  2. Construct a plain JS object with buffer set to that ArrayBuffer, byteOffset: 0, and a large spoofed byteLength (e.g., 1000000).
  3. Call new TextEncoder().encodeInto(largeString, fakeView) with a long string (e.g., 'A'.repeat(100000)).
  4. encodeInto writes UTF-8 bytes past the 8-byte allocation, corrupting adjacent heap memory.

+// Regression test: TextEncoder.encodeInto() and TextDecoder.decode() accept a
+// duck-typed TypedArray view -- any object exposing buffer/byteOffset/byteLength.
+// The view geometry was previously trusted without checking that
+// byteOffset + byteLength stays within the backing ArrayBuffer, so a plain
+// object with out-of-bounds values produced an out-of-bounds write/read relative
+// to the buffer. Such views must now throw instead. Both APIs share the same
+// bounds check, so exercising the write path is sufficient to cover it.
+"use strict";
+
+print('typedarray-view-bounds');
+// CHECK-LABEL: typedarray-view-bounds
+
+const enc = new TextEncoder();
+
+// Out of bounds because byteOffset is past the end (exploit shape).
+try {
+  const ab = new ArrayBuffer(16);
+  enc.encodeInto("A".repeat(0x1000), {
+    buffer: ab,
+    byteOffset: 0x100000,
+    byteLength: 0x1000,
+  });
+  print("FAIL: OOB byteOffset did not throw");
+} catch (e) {
+  print(e.message);
+  // CHECK-NEXT: The second argument should be a Uint8Array
+}
+
+// Out of bounds because byteLength runs past the end (offset is valid).
+try {
+  const ab = new ArrayBuffer(16);
+  enc.encodeInto("A".repeat(17), {buffer: ab, byteOffset: 0, byteLength: 17});
+  print("FAIL: OOB byteLength did not throw");
+} catch (e) {
+  print(e.message);
+  // CHECK-NEXT: The second argument should be a Uint8Array
+}
+
+// In bounds: byteOffset + byteLength == size must be accepted (off-by-one guard).
+const ab1 = new ArrayBuffer(10);
+let r = enc.encodeInto("ABCD", {buffer: ab1, byteOffset: 6, byteLength: 4});
+print(r.read + " " + r.written + " " + new Uint8Array(ab1).slice(6).join(","));
+// CHECK-NEXT: 4 4 65,66,67,68
+
+// In bounds: empty view at the very end (byteOffset == size, byteLength == 0).
+const ab2 = new ArrayBuffer(4);
+r = enc.encodeInto("xyz", {buffer: ab2, byteOffset: 4, byteLength: 0});
+print(r.read + " " + r.written);
+// CHECK-NEXT: 0 0
+
+// A real Uint8Array still round-trips through the normal path.
+const view = new Uint8Array(8);
+r = enc.encodeInto("hello", view);
