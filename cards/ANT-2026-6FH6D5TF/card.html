ANT-2026-6FH6D5TF: Hardcoded Realtime tenant-credential encryption key with no override

In docker/docker-compose.yml the Realtime service sets DB_ENC_KEY to the literal string 'supabaserealtime' rather than interpolating from .env like every adjacent secret. The variable is absent from .env.example and untouched by generate-keys.sh, so users who follow the documented secret-rotation guidance still ship the public default. Realtime uses this key to AES-encrypt tenant database credentials (including the Postgres password) stored in the _realtime schema. An attacker who can read those tables — via backup leak, read-only SQLi, or misconfigured role — can decrypt the credentials offline and escalate to full database control.

Target

Project: supabase/supabase
Location: docker/docker-compose.yml:314
Discovery: static analysis — not yet dynamically reproduced

Technical Details

DB_ENC_KEY is assigned a fixed literal instead of a ${VAR} reference, and no generation/override path exists in .env.example or generate-keys.sh. Because the key is public in the repository, the AES encryption applied to tenant credentials in the _realtime schema provides no confidentiality against anyone who can read the ciphertext.

Reproduction

  1. Obtain read access to _realtime.extensions / _realtime.tenants (backup dump, SQLi, or over-privileged role)
  2. Extract the AES-encrypted tenant database credential fields
  3. Decrypt them offline using the publicly-known key 'supabaserealtime'
  4. Use the recovered Postgres superuser password to authenticate with full privileges

[No reproducer or sanitizer output attached — request from security-cvd@anthropic.com if needed.]

Suggested Fix

Source DB_ENC_KEY from deployment-specific configuration (a ${VAR} in .env) with no functional hardcoded fallback, add it to .env.example and generate-keys.sh, and include it in the documented secret-rotation workflow.
