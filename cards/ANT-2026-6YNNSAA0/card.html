ANT-2026-6YNNSAA0: Image-generation function fetches arbitrary caller URL with service-role in scope

The openai-image-generation example edge function reads imageUrl from the request body, fetches it with fetch(imageUrl), and uploads the resulting blob to a Storage bucket using the service-role key. Nothing restricts the URL to OpenAI's CDN, so an authenticated caller can point it at cloud metadata endpoints, VPC-internal services reachable from the edge egress, or arbitrarily large files. The attacker can then read the exfiltrated response body from the Storage bucket, or abuse the fetch loop to inflate the deployer's storage costs. The only gate is verify_jwt = true, so any holder of a valid project JWT (anon sign-up or user account) can trigger it.

Target

Project: supabase/supabase
Location: examples/edge-functions/supabase/functions/openai-image-generation/index.ts:44
Discovery: static analysis — not yet dynamically reproduced

Technical Details

The root cause is trusting a client-supplied URL as if it were the server-generated OpenAI result: the handler does const img = await fetch(imageUrl); const blob = await img.blob(); on an unvalidated imageUrl taken directly from the JSON body, with no hostname allow-list, scheme check, or size cap, while running with service-role privileges.

Reproduction

  1. Authenticate to the target Supabase project to obtain a valid JWT
  2. Invoke the openai-image-generation function with body {"imageUrl":"http://169.254.169.254/latest/meta-data/iam/security-credentials/"} (or another internal URL)
  3. Function fetches the URL server-side and uploads the response blob to the images Storage bucket under a predictable path
  4. Download the stored object from the bucket to read the internal response; optionally repeat with multi-GB URLs to inflate storage costs

[No reproducer or sanitizer output attached — request from security-cvd@anthropic.com if needed.]

Suggested Fix

Call OpenAI server-side and consume the returned URL without ever accepting a URL from the client; alternatively, validate that new URL(imageUrl).hostname is in an allow-list of OpenAI CDN hosts and the scheme is https before fetching, and cap the downloaded size.
