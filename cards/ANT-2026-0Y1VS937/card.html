ANT-2026-0Y1VS937: Heap underflow in H.264 xchg_mb_border via slice_num/sentinel collision

In FFmpeg's H.264 decoder, slice_table (h264dec.h) is a uint16_t array memset to 0xFFFF as a 'no slice' sentinel, while slice_num = ++h->current_slice is an uncapped int. At slice 65535, slice_num == 0xFFFF, so comparisons against the never-written spare slice_table entries (one per row, mb_stride = mb_width + 1) spuriously match. This defeats the deblock_topleft check in h264_mb.c:532 and the topleft/top guards in h264_mvpred.h:564, leaving deblock_top and deblock_topleft true at mb_x == 0. xchg_mb_border then computes top_border_m1 = sl->top_borders[top_idx][sl->mb_x - 1] (index -1, 96 bytes below the allocation) and performs AV_SWAP64 at offsets -88, -72, -56 — three 8-byte OOB writes whose values are decoded pixel data (src_y - 7) and thus attacker-controlled via DCT coefficients. Trigger requires disable_deblocking_filter_idc = 2 in the slice header, which the attacker sets.

Target

Project: ffmpeg/ffmpeg
Version: all releases since the original 2003 H.264 decoder commit through current master (f73849887c)
Location: libavcodec/h264_mb.c:561 (xchg_mb_border)

Technical Details

ASAN: 'heap-buffer-overflow ... READ of size 8 at 0x51b000008528 ... located 88 bytes before 1460-byte region' at h264_mb.c:561. ASan reports the read first, but XCHG is AV_SWAP64 ({tmp=b; b=a; a=tmp}), so a non-instrumented build unconditionally performs the paired write as well. Root cause: the 0xFFFF sentinel in a uint16_t slice_table is reachable by the unbounded int slice_num, turning 'is this macroblock in my slice?' guards into tautologies for spare entries and bypassing the mb_x > 0 protection path.

Reproduction

  1. Craft an H.264 picture with ~65536 slices so that ++h->current_slice reaches 0xFFFF.
  2. Set disable_deblocking_filter_idc = 2 so the deblock_topleft check consults slice_table instead of mb_x > 0.
  3. On the 0xFFFF-th slice, spare slice_table entries (still 0xFFFF) compare equal to slice_num; guards in h264_mb.c:532 and h264_mvpred.h:564 fail open.
  4. At mb_x = 0, xchg_mb_border indexes top_borders[top_idx][-1] and executes XCHG/AV_SWAP64 at base-88, base-72, base-56.
  5. Choose DCT coefficients so decoded src_y pixels — the values swapped in — are attacker-chosen bytes.

[No reproducer or sanitizer output attached — request from security-cvd@anthropic.com if needed.]

Suggested Fix

In h264_slice_init (libavcodec/h264_slice.c), reject the slice before incrementing when h->current_slice >= 0xFFFE, returning AVERROR_INVALIDDATA so slice_num can never equal the 0xFFFF sentinel. Patch/PR provided.

                    6 * (h->ps.sps->bit_depth_luma - 8);
 
+    // slice_table is uint16_t initialized to 0xFFFF as a sentinel.
+    if (h->current_slice >= 0xFFFE) {
+        av_log(h->avctx, AV_LOG_ERROR, "Too many slices (%d)\n", h->current_slice + 1);
+        return AVERROR_PATCHWELCOME;
+    }
+
     sl->slice_num       = ++h->current_slice;
 
     if (sl->slice_num)
